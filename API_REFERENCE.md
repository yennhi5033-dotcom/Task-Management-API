# Task Management API Reference

This document lists every HTTP route exposed by the project, along with request payloads and response shapes, so the frontend can integrate without reading the source code.

## Base URL

- Local default: `http://localhost:3001`
- API prefix: `/api/tasks`

## Data Model

### `Task`

| Field | Type | Required | Default | Notes |
| --- | --- | --- | --- | --- |
| `_id` | string | yes | generated by MongoDB | ObjectId as string |
| `title` | string | yes | - | Task title |
| `description` | string | no | `""` | Task description |
| `status` | string | no | `todo` | Enum: `todo`, `doing`, `done` |
| `priority` | string | no | `medium` | Enum: `low`, `medium`, `high` |
| `dueDate` | string or null | no | `null` | Stored as ISO date-time |
| `createdAt` | string | yes | generated by Mongoose | ISO date-time |
| `updatedAt` | string | yes | generated by Mongoose | ISO date-time |
| `__v` | number | yes | generated by Mongoose | Version key |

### Notes

- `status` is lowercased automatically by the schema setter.
- `PATCH /:id/status` only allows sequential transitions:
  - `todo -> doing`
  - `doing -> done`
- Skipping a step returns a `400`.
- `DELETE` returns no response body.

## Common Error Response

All error responses in this project use the same shape:

```json
{
  "message": "Human readable error message"
}
```

## Routes

- No query params

### 6) `PATCH /api/tasks/:id/status`

Update task status with sequential validation.

Allowed flow:

`todo -> doing -> done`

#### Path Params

| Name | Type | Required | Notes |
| --- | --- | --- | --- |
| `id` | string | yes | MongoDB ObjectId |

#### Request Body

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `status` | string | yes | Must be one of `todo`, `doing`, `done` |

#### Example Request

```json
{
  "status": "doing"
}
```

#### Success Response

- Status: `200 OK`
- Body: updated `Task`

```json
{
  "_id": "66c14e7f5fd2b8a8fb2d3c11",
  "title": "Hoc Express.js",
  "description": "Hoan thanh REST API",
  "status": "doing",
  "priority": "high",
  "dueDate": "2026-08-20T00:00:00.000Z",
  "createdAt": "2026-08-16T04:00:00.000Z",
  "updatedAt": "2026-08-16T04:15:00.000Z",
  "__v": 0
}
```

#### Error Responses

- `400 Bad Request` if `status` is missing

```json
{
  "message": "Status is required"
}
```

- `400 Bad Request` if status value is invalid

```json
{
  "message": "Status must be todo, doing, or done"
}
```

- `400 Bad Request` if transition is not allowed

```json
{
  "message": "Cannot change status from todo to done"
}
```

- `404 Not Found`

```json
{
  "message": "Task not found"
}
```

- `400 Bad Request` for any error thrown during validation or transition logic

```json
{
  "message": "any error message from the server"
}
```

## Frontend Integration Summary

Recommended call sequence for FE:

1. `GET /api/tasks` to load the task list.
2. `POST /api/tasks` to create a new task.
3. `GET /api/tasks/:id` to open task details.
4. `PUT /api/tasks/:id` to edit a task.
5. `PATCH /api/tasks/:id/status` to move task status forward.
6. `DELETE /api/tasks/:id` to remove a task.

## Important Implementation Notes

- The API uses JSON only for the task endpoints.
- `dueDate` is stored in MongoDB as a date and returned in ISO 8601 format.
- If the frontend sends extra fields, Mongoose may ignore fields that are not part of the schema.
- All timestamps are generated automatically by Mongoose.
